Guide pédagogique

Écrire un workflow CSFlow : tous les mots-clés expliqués

Ce guide présente chaque clé du fichier YAML, ce qu'elle fait, quand l'utiliser et comment éviter les erreurs. Les tableaux viennent directement du schéma du projet (10 types d'étape, 34 clés) ; chaque exemple a été validé par le moteur.

1. Comprendre en deux minutes

Un workflow CSFlow est une recette de cuisine écrite dans un fichier texte. Chaque ligne de la recette est une étape ; chaque étape a un verbe (son type) qui dit ce qu'elle fait.

  • Les étapes s'exécutent dans l'ordre de la liste, une par une.
  • Chaque étape laisse un résultat que les suivantes peuvent réutiliser, avec la syntaxe {{id.output}}.
  • On peut bifurquer (une étape peut en sauter une autre, ou le workflow peut se séparer selon la réponse d'un humain) et s'arrêter avec une étape de fin.

Un exemple annoté

Ce petit workflow écrit un fichier puis affiche ce qu'il a écrit. Chaque pastille bleue renvoie à l'explication qui suit.

rapport_hebdo.yaml
name: Rapport hebdo1description: Écrit un rapport puis affiche son contenu.2inputs:3  projet: Portail usagerssteps:4  - id: ecrire5    type: file_write6    path: 'tmp\rapport.txt'7    content: "Rapport du projet {{projet}} du {{today}}"  - id: afficher    type: log    message: "Fichier écrit : {{ecrire.output}}"8
  1. 1name : le nom du workflow, affiché dans l'interface.
  2. 2description : une phrase pour dire à quoi il sert (facultatif).
  3. 3inputs : des valeurs de départ, réutilisables partout avec {{projet}} (facultatif).
  4. 4steps : la liste des étapes. C'est la seule clé obligatoire.
  5. 5id : le nom de l'étape. Il permet de relire son résultat plus loin : {{ecrire.output}}.
  6. 6type : le verbe de l'étape. Ici « écrire un fichier ».
  7. 7path et content : les paramètres propres au type file_write.
  8. 8{{ecrire.output}} : le résultat de l'étape précédente, inséré dans le message.
À retenir

Il n'y a que trois niveaux de mots-clés : ceux du fichier, ceux que toute étape accepte, et ceux propres à chaque type d'étape. La section suivante en fait la carte.

3. Les clés du fichier

Quatre clés, écrites tout en haut du fichier. Seule steps est obligatoire.

namefacultatiftexte

Schéma : « nom du workflow (affiché dans l'interface) »

Le nom qui apparaît dans la liste des workflows et au-dessus du graphe.

Exemple : name
name: Préparation du COPIL

descriptionfacultatiftexte

Schéma : « description du workflow »

Une phrase qui résume le workflow. Elle est affichée au lancement. Si elle contient un deux-points suivi d'un espace, mettez-la entre guillemets.

Exemple : description
description: "Du plan de projet au rapport : orchestration Python, analyse CSAgent"

inputsfacultatifdictionnaire

Schéma : « variables d'entrée, utilisables dans tout le workflow avec {{nom}} »

Des valeurs définies une seule fois, en haut. On les réutilise partout avec {{nom}}. Pratique pour changer un dossier ou un nom de projet à un seul endroit.

Exemple : inputs
inputs:  projet: Portail usagers  dossier: 'tmp\mon-projet'

stepsobligatoireliste

Schéma : « liste des étapes »

La liste des étapes. Elle ne peut pas être vide, et le workflow démarre toujours par la première étape de la liste.

Exemple : steps
steps:  - id: premiere    type: log    message: Bonjour

4. Les clés de toute étape

Ces huit clés fonctionnent sur n'importe quel type d'étape. Seules id et type sont obligatoires.

Astuce

Pensez-y comme à l'étiquette collée sur chaque étape : qui elle est (id, type, description), quand elle s'exécute (skip_if, next, on_approve, on_reject) et que faire si ça casse (continue_on_error).

idobligatoiretexte

Schéma : « identifiant unique de l'étape ; son résultat s'utilise avec {{id.output}} »

Le nom de l'étape. Il doit être unique dans le fichier. Il sert à deux choses : désigner l'étape dans next, on_approve ou on_reject, et lire son résultat avec {{id.output}}. Choisissez-le court, sans espace (par exemple analyse_risques).

Exemple : id
- id: analyse  type: log  message: Début- id: suite  type: log  message: "L'analyse a produit : {{analyse.output}}"

typeobligatoiretexte

Schéma : « type d'étape (liste : python engine.py --nodes) »

Le verbe : il décide de ce que fait l'étape et de quels paramètres elle accepte. Il en existe dix (voir la section 5). Une faute de frappe est détectée avant l'exécution, avec une suggestion.

Exemple : type
- id: lecture  type: file_read  path: 'tmp\notes.txt'

descriptionfacultatiftexte

Schéma : « libellé affiché dans l'interface »

Le libellé lisible affiché dans l'interface (graphe, liste des étapes). Facultatif : sans lui, c'est l'id qui s'affiche. Mettez-le entre guillemets s'il contient « : ».

Exemple : description
- id: lecture  type: file_read  description: "Lecture des notes de réunion"  path: 'tmp\notes.txt'

skip_iffacultatiftexte

Schéma : « expression Python ; si elle est vraie, l'étape est ignorée. Ex : "'{{statut.output}}' != 'ROUGE'" »

Une condition d'exclusion : si elle est vraie, l'étape est ignorée (son état devient skipped, son résultat est vide) et le workflow passe à la suite. C'est une expression Python simple (comparaisons, and, or, not, in). Les {{…}} sont remplacées avant le calcul : entourez de quotes celles qui sont du texte, pas celles qui sont des nombres. Si l'expression est invalide, elle est considérée comme fausse et l'étape s'exécute.

Exemple : skip_if
- id: escalade  type: log  level: warn  skip_if: "'{{statut.output}}' != 'ROUGE'"  message: "Statut rouge : prévenir le sponsor"

continue_on_errorfacultatiftrue / false

Schéma : « true = le workflow continue même si l'étape échoue »

Tolérer l'échec. Par défaut, une étape en erreur arrête tout le workflow. Avec true, l'erreur est notée et le workflow continue : vous pouvez lire {{id.returncode}} ou {{id.status}} pour décider quoi faire ensuite.

Exemple : continue_on_error
- id: essai  type: shell  cmd: 'python tmp\script.py'  continue_on_error: true

nextfacultatiftexte

Schéma : « id de l'étape suivante (défaut : l'étape suivante dans la liste) »

Sauter à l'étape indiquée au lieu de la suivante dans la liste. Indispensable pour rejoindre une étape de fin après une bifurcation.

Exemple : next
- id: diffusion  type: log  message: Rapport diffusé  next: fin- id: annule  type: end  message: Annulé- id: fin  type: end  message: Terminé

on_approvefacultatiftexte

Schéma : « human_approval : id de l'étape suivante si approuvé »

Réservée à human_approval : l'étape à exécuter si l'humain approuve.

Un exemple complet est donné avec le type human_approval (section 5) et dans le tutoriel.

on_rejectfacultatiftexte

Schéma : « human_approval : id de l'étape suivante si rejeté »

Réservée à human_approval : l'étape à exécuter si l'humain rejette.

Un exemple complet est donné avec le type human_approval (section 5) et dans le tutoriel.

5. Les dix types d'étape

Chaque fiche suit le même plan : à quoi ça sert, quels paramètres, ce que l'étape produit, un exemple, et les pièges.

  • 🤖 agent : Envoie une instruction à CSAgent et suit son raisonnement en direct ; sortie : sa dernière réponse.
  • ⚡ shell : Exécute une commande shell (cmd.exe sous Windows, bash ailleurs).
  • ⚙️ transform : Évalue une expression Python pour transformer des données.
  • 📄 file_read : Lit un fichier texte ; sortie : output (le contenu).
  • ✏️ file_write : Écrit (ou remplace) un fichier texte ; les dossiers manquants sont créés.
  • 🌐 http_get : Requête HTTP GET ; sorties : body, status_code.
  • 🌐 http_post : Requête HTTP POST ; sorties : body, status_code.
  • 👤 human_approval : Met le workflow en pause jusqu'à ce qu'un humain approuve ou rejette.
  • 📝 log : Affiche un message dans la console et dans le log de l'interface.
  • 🏁 end : Termine le workflow (étape finale, aucune étape ne peut la suivre).

🤖agent🤖 IA

Envoie une instruction à CSAgent et suit son raisonnement en direct ; sortie : sa dernière réponse.

En image : Un collaborateur à qui l'on confie une consigne écrite.

Quand l'utiliser ?

Pour tout ce qui demande de lire, comprendre ou rédiger : analyser des notes, résumer un rapport, corriger du code. Pour des chiffres, préférez shell ou transform : un calcul de code est exact et reproductible.

Ses paramètres

Paramètres de agent
CléStatutValeurRôle
promptobligatoiretexteinstruction en langage naturel envoyée à CSAgent
csagent_urlfacultatiftexteURL de CSAgent (défaut http://localhost:8080)
csagent_keyfacultatiftexteclé d'API (défaut demo-secret)
timeoutfacultatifnombre (secondes)secondes sans donnée avant abandon (défaut 180)
auto_confirmfacultatiftrue / falsetrue = approuver automatiquement les demandes de confirmation de CSAgent

Avec les clés communes à toutes les étapes (id, type, description, skip_if, continue_on_error, next…).

Ce qu'elle produit

Champs produits par agent (à lire avec {{id.champ}})
ChampContenu
{{id.output}}la dernière réponse de CSAgent
{{id.thoughts}}son raisonnement, étape par étape

Exemple

Exemple : agent
- id: risques  type: agent  description: Analyse des risques  prompt: |    Lis le fichier tmp/notes.txt et liste les risques cités,    un par ligne, du plus grave au moins grave.  auto_confirm: true  timeout: 300

À savoir

  • Gardez le prompt court : il est transmis dans l'adresse de la requête.
  • N'utilisez que des chemins relatifs : CSAgent n'écrit que dans son dossier courant (lancez-le depuis workflow\).
  • Sans auto_confirm, CSAgent demande une confirmation avant d'écrire un fichier : l'interface affiche Approuver / Rejeter. Avec auto_confirm: true, tout est approuvé automatiquement : ajoutez alors une validation humaine plus loin.
  • timeout compte les secondes sans aucune donnée reçue, pas la durée totale.

⚡shell⚡ Exécution

Exécute une commande shell (cmd.exe sous Windows, bash ailleurs).

En image : Taper une commande dans un terminal.

Quand l'utiliser ?

Pour lancer un script Python, un outil en ligne de commande ou compter des lignes. C'est l'étape qui lance vos commandes et scripts, et donc vos calculs exacts : la commande tourne dans cmd.exe sous Windows et bash ailleurs.

Ses paramètres

Paramètres de shell
CléStatutValeurRôle
cmdobligatoiretextecommande exécutée par cmd.exe (Windows) ou bash ; sorties : output, stdout, stderr, returncode
timeoutfacultatifnombre (secondes)secondes avant arrêt du processus (défaut 60)

Avec les clés communes à toutes les étapes (id, type, description, skip_if, continue_on_error, next…).

Ce qu'elle produit

Champs produits par shell (à lire avec {{id.champ}})
ChampContenu
{{id.output}}stdout + stderr rassemblés
{{id.stdout}}la sortie normale
{{id.stderr}}les messages d'erreur
{{id.returncode}}le code de retour (0 = succès)

Exemple

Exemple : shell
- id: compter  type: shell  description: Compter les lignes du rapport  cmd: 'type tmp\rapport.md | find /c /v ""'  timeout: 30

À savoir

  • Sous Windows, entourez la commande de quotes simples YAML : le \ reste ainsi un simple caractère.
  • Un code de retour différent de 0 est une erreur : le workflow s'arrête, sauf continue_on_error: true (lisez alors {{id.returncode}}).
  • La commande est arrêtée au bout de timeout secondes (60 par défaut).

⚙️transform⚡ Exécution

Évalue une expression Python pour transformer des données.

En image : Une calculatrice.

Quand l'utiliser ?

Pour un petit calcul ou un test sans lancer de programme : arrondir un montant, compter les éléments d'une liste, comparer deux valeurs.

Ses paramètres

Paramètres de transform
CléStatutValeurRôle
expressionobligatoiretexteexpression Python évaluée ; les {{variables}} sont substituées avant

Avec les clés communes à toutes les étapes (id, type, description, skip_if, continue_on_error, next…).

Ce qu'elle produit

Champs produits par transform (à lire avec {{id.champ}})
ChampContenu
{{id.output}}le résultat, en texte
{{id.value}}le résultat brut (nombre, liste…)

Exemple

Exemple : transform
- id: total_ttc  type: transform  expression: "round(float('{{ht.output}}') * 1.2, 2)"

À savoir

  • Les {{variables}} sont remplacées avant le calcul : mettez celles qui contiennent du texte entre quotes, comme '{{x.output}}'.
  • Fonctions disponibles : len, int, float, str, bool, round, sum, min, max, abs, list, dict, set, tuple, sorted, reversed, enumerate, zip, range, map, filter, any, all. Rien d'autre (pas d'import).

👤human_approval👤 Humain

Met le workflow en pause jusqu'à ce qu'un humain approuve ou rejette.

En image : Un feu orange : le workflow attend qu'un humain passe au vert.

Quand l'utiliser ?

Avant toute action qu'on ne veut pas laisser partir toute seule : diffusion, suppression, envoi à la direction. C'est la seule étape qui crée une bifurcation : une suite si l'humain approuve, une autre s'il rejette.

Ses paramètres

Paramètres de human_approval
CléStatutValeurRôle
messagefacultatiftextequestion posée à l'humain (défaut « Approve to continue? »)

Avec les clés communes à toutes les étapes (id, type, description, skip_if, continue_on_error, next…).

Ce qu'elle produit

Champs produits par human_approval (à lire avec {{id.champ}})
ChampContenu
{{id.output}}approved ou rejected
{{id.answer}}identique à output

Exemple

Exemple : human_approval
- id: validation  type: human_approval  message: "Diffuser le rapport au COPIL ?"  on_approve: diffusion  on_reject: annule

À savoir

  • Renseignez on_approve et on_reject : sans l'un des deux, le workflow s'arrête sur cette branche (la validation vous prévient).
  • Dans l'interface, sans réponse au bout de 10 minutes, la demande est considérée comme rejetée.
  • La réponse est disponible ensuite : {{validation.output}} vaut approved ou rejected.

6. Réutiliser un résultat : les variables {{…}}

Les doubles accolades sont des trous à remplir. Juste avant d'exécuter une étape, CSFlow remplace chaque {{…}} de ses paramètres par la valeur correspondante.

Les variables disponibles
ÉcritureValeur
{{today}}la date du jour, au format AAAA-MM-JJ
{{now}}la date et l'heure, au format AAAA-MM-JJTHH:MM:SS
{{env.NOM}}la variable d'environnement « NOM » (vide si elle n'existe pas)
{{nom}}une variable déclarée dans inputs
{{id.output}}le résultat de l'étape « id » ; {{id}} seul revient au même
{{id.champ}}un autre champ du résultat : returncode, status_code, status…

Les champs d'un résultat

Toute étape produit au moins output (son résultat, en texte) et status (son état : ok, error ou skipped). Chaque type ajoute ses propres champs :

endoutput

Trois règles à connaître

  • Une variable inconnue est remplacée par du vide, sans erreur. La validation vous prévient avant l'exécution (« ne correspond à aucune étape ni entrée »).
  • Les inputs et les résultats sont lisibles par toutes les étapes qui viennent après, pas seulement la suivante.
  • Les résultats sont du texte. Pour comparer un nombre dans skip_if, écrivez-le sans quotes ({{id.returncode}} == 0). Pour comparer un texte, mettez des quotes ('{{id.output}}' == 'ROUGE').
Exemple : réutiliser un résultat
- id: compter  type: shell  cmd: 'type tmp\rapport.md | find /c /v ""'- id: bilan  type: log  message: "Le rapport compte {{compter.output}} lignes (code {{compter.returncode}}) — {{today}}"

7. Enchaîner les étapes

Par défaut, tout est simple : une étape après l'autre. Quatre outils permettent de dévier de ce chemin.

L'ordre naturel

Sans rien préciser, l'étape suivante est celle qui est juste en dessous dans la liste. Après la dernière, le workflow se termine.

Sauter avec next

next désigne l'étape à exécuter ensuite, quelle que soit sa place dans la liste.

Bifurquer avec human_approval

Après une validation humaine, le workflow prend l'une des deux branches.

Ignorer avec skip_if

L'étape est évitée si la condition est vraie, et le workflow continue avec la suivante.

Comment le moteur choisit l'étape suivante

  1. L'étape est de type end : le workflow s'arrête.
  2. L'étape est de type human_approval : il suit on_approve si l'humain a approuvé, sinon on_reject. Si la clé manque, il s'arrête.
  3. L'étape a un next : il va à cette étape.
  4. Sinon : il passe à l'étape suivante dans la liste (ou se termine s'il n'y en a plus).
Attention

Après une branche, l'étape suivante « dans la liste » est peut-être celle de l'autre branche. Ajoutez un next à la fin de chaque branche pour rejoindre la bonne étape de fin (voir le tutoriel, étape 4).

Quand une étape échoue

Une étape est en erreur quand sa commande échoue, qu'un fichier manque, qu'une requête renvoie un code hors 200 à 299, etc. Par défaut, le workflow s'arrête à cet endroit. Avec continue_on_error: true, il continue : c'est à vous de tester {{id.status}} ou {{id.returncode}} pour réagir.

8. Les pièges courants

Huit erreurs que tout le monde fait au début. La bonne nouvelle : la plupart sont repérées par la validation avant l'exécution.

  1. Les chemins Windows et les quotes. Dans une valeur contenant des \, utilisez des quotes simples : path: 'tmp\rapport.md'. Avec des guillemets doubles, le \ serait interprété par YAML.
  2. Un deux-points dans un texte. Une valeur qui contient « : » suivi d'un espace doit être entre guillemets : description: "Étape : analyse". Sinon YAML croit lire une nouvelle clé.
  3. Des accolades dans un fichier à écrire. Dans file_write, les {{…}} de content sont remplacées avant l'écriture. Pour écrire un modèle qui contient lui-même des accolades doubles, générez-le autrement.
  4. Oublier le next après une branche. Sans next, la fin de la branche « approuvé » enchaîne sur l'étape située juste dessous, qui est souvent celle de la branche « rejeté ».
  5. Comparer un texte sans quotes. Dans skip_if, écrivez '{{statut.output}}' != 'ROUGE' (avec des quotes) pour du texte, et {{id.returncode}} == 0 (sans quotes) pour un nombre.
  6. Des prompts trop longs ou des chemins absolus avec CSAgent. Le prompt voyage dans l'adresse de la requête : restez bref. Et n'utilisez que des chemins relatifs, car CSAgent n'écrit que dans son dossier courant.
  7. Des tabulations dans le YAML. YAML s'indente avec des espaces, jamais des tabulations. Deux espaces par niveau est la convention.
  8. Une faute de frappe sur une clé. Une clé inconnue n'est pas une erreur mais un avertissement : elle est ignorée (mesage au lieu de message donne un message vide). Lancez la validation pour les repérer.

9. Tutoriel : construire un workflow pas à pas

Quatre workflows de plus en plus riches. Copiez-les dans le dossier workflows, ils passent tous la validation.

  1. Le plus petit workflow

    Un seul type d'étape, un seul message. C'est le point de départ de tous les autres.

    Étape 1 : Le plus petit workflow
    name: Bonjour CSFlowdescription: Un workflow minimal.steps:  - id: salut    type: log    message: "Bonjour depuis CSFlow !"

    Vous avez utilisé : name, description, steps, id, type, message.

  2. Enchaîner et réutiliser un résultat

    On écrit un fichier, on le relit, puis on affiche son contenu grâce à {{relire.output}}.

    Étape 2 : Enchaîner et réutiliser un résultat
    name: Écrire puis reliresteps:  - id: ecrire    type: file_write    path: 'tmp\bonjour.txt'    content: "Rapport généré le {{today}}"  - id: relire    type: file_read    path: 'tmp\bonjour.txt'  - id: afficher    type: log    level: success    message: "Contenu du fichier : {{relire.output}}"

    Nouveautés : {{today}}, {{id.output}}, les types file_write et file_read, level.

  3. Un paramètre d'entrée et une étape conditionnelle

    On tolère l'échec d'une commande, puis on n'affiche l'alerte que si elle a échoué.

    Étape 3 : Un paramètre d'entrée et une étape conditionnelle
    name: Contrôle conditionnelinputs:  projet: Portail usagerssteps:  - id: compter    type: shell    description: Compter les lignes du fichier    cmd: 'type tmp\bonjour.txt | find /c /v ""'    continue_on_error: true  - id: alerte    type: log    level: warn    skip_if: "{{compter.returncode}} == 0"    message: "Fichier introuvable pour le projet {{projet}}"  - id: ok    type: log    level: success    message: "{{projet}} : {{compter.output}} lignes"

    Nouveautés : inputs, shell, continue_on_error, skip_if, {{id.returncode}}.

  4. Une validation humaine et deux issues

    Le workflow s'arrête et attend une décision. Remarquez le next qui évite de tomber dans la branche « rejeté ».

    Étape 4 : Une validation humaine et deux issues
    name: Diffusion validéesteps:  - id: rapport    type: file_write    path: 'tmp\rapport.txt'    content: "Rapport du {{today}}"  - id: validation    type: human_approval    message: "Diffuser le rapport ?"    on_approve: diffusion    on_reject: annule  - id: diffusion    type: log    level: success    message: "Rapport diffusé."    next: fin  - id: annule    type: end    message: "Diffusion annulée."  - id: fin    type: end    message: "Rapport diffusé avec succès."

    Nouveautés : human_approval, on_approve, on_reject, next, end.

10. Vérifier son workflow avant de le lancer

Inutile de lancer un workflow pour savoir s'il est bien écrit : trois outils le contrôlent à votre place.

Dans le terminal

Commandes (depuis le dossier workflow)
python engine.py --nodespython engine.py --check workflows\mon_workflow.yamlpython engine.py --check workflows\*.yaml
  • --nodes affiche tous les types et leurs paramètres : c'est la référence à jour.
  • --check valide sans exécuter, et indique la ligne de chaque problème.
Exemple de résultat
✗ mauvais.yaml:5  étape « a » : type « shel » inconnu — vouliez-vous dire « shell » ?⚠ mauvais.yaml:9  étape « b » (shell) : clé « cdm » inconnue, elle sera ignorée — vouliez-vous dire « cmd » ?✗ mauvais.yaml:21 étape « e » : « on_approve: dd » ne désigne aucune étape — vouliez-vous dire « d » ?

Le symbole ✗ est une erreur (le workflow ne démarre pas) ; ⚠ est un avertissement (il démarre, mais quelque chose est probablement faux).

Dans VS Code

Avec l'extension « YAML » de Red Hat, ajoutez cette ligne tout en haut de votre fichier. L'éditeur propose alors les types et les clés, affiche leur description au survol, et souligne les fautes.

Première ligne du fichier .yaml
# yaml-language-server: $schema=../csflow.schema.json

Au lancement

Le moteur et l'interface appliquent la même validation avant chaque exécution : une erreur empêche le démarrage, un avertissement s'affiche dans le journal.

Ce que vérifie la validation

  • le YAML est lisible, et steps est une liste non vide ;
  • chaque étape a un type connu, et un id unique ;
  • les paramètres obligatoires du type sont présents ;
  • les clés inconnues sont signalées, avec une suggestion ;
  • next, on_approve et on_reject désignent des étapes qui existent ;
  • les {{variables}} correspondent à une étape, un input ou une variable prévue.
